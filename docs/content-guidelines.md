# Content guidelines

## An exploration's editorial contract

1. Start from a recognizable system and a concrete problem, before naming a solution.
2. Evolve that one system scene by scene: each decision solves a problem and reveals the next.
3. Let the reader run each step and change its parameters; show results as numbers and in the diagram, not only in prose.
4. Compare each decision with the previous one: what got better, what got worse.
5. Avoid "best practice" labels; added complexity is a cost.
6. List model assumptions, omissions, and what the model does not prove.
7. Cite further reading and distinguish general ideas from product-specific guarantees.

## Correctness and attribution

Use precise terms. Model output is an estimate: never present it as measured database performance. Describe conditional guarantees in the context of implementation and configuration. Do not present a queue-based push architecture as a required upgrade of a pull transfer.

Use original scenarios, text, diagrams, and exercises. Do not organize explorations to mirror a copyrighted book or trace figures. Mention conceptual inspiration separately from technical evidence. Link primary implementation documentation for product claims; name book authors and publication details without implying affiliation. Quote only when necessary and narrowly, with attribution. Review sources whenever an exploration's claims change.

## Accessible experiments

Use native labeled buttons, inputs, checkboxes, and selects. Supply textual equivalents for graphical node values and links. Show status in words as well as color. Keep controls reachable with visible focus, support mobile reflow, and respect reduced motion. Important read feedback belongs in a polite live region; do not announce the entire event history on every action. Provide readable explanations and a worked scenario without JavaScript.

## Model limitations

Every exploration names its time model, delivery ordering, failure boundaries, persistence behavior, and omitted mechanisms. Models teach causality, not performance predictions. A simulated behavior is not evidence that a real database provides that behavior. Review a deterministic scenario against both code and prose before publication.
